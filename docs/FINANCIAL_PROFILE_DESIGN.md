# Financial Profile, Tier 0, Forecast–Budget–Goal และ Alert Layer — ร่าง design

ร่าง 30 ต.ค. 2026 · สถานะ: C1–C6 และตาราง D **[ยืนยันครบ]** บันทึกไว้ใน [DECISIONS](DECISIONS.md) แล้ว

ป้ายในเอกสาร: **[ปัจจุบัน]** = พฤติกรรมของโค้ดตอนนี้ · **[ยืนยัน]** = ผู้ใช้ยืนยันแล้ว (ใน [DECISIONS](DECISIONS.md) หรือในการตอบรอบนี้) · **[รอ]** = ข้อเสนอที่ยังต้องตัดสิน

หลักเมื่อโจทย์ขัดกับเอกสารโปรเจกต์ **[ยืนยัน]**: ให้ยึดเอกสารโปรเจกต์ แล้วแจ้งผู้ใช้ ไม่ทำตามโจทย์เงียบ ๆ

## 0. ข้อขัดแย้ง C1–C6 — ผลการตัดสิน **[ยืนยัน 30 ต.ค. 2026]**

| # | เรื่อง | ผลการตัดสิน |
|---|---|---|
| C1 | Forecast Gate | ใช้ **30 รายจ่าย / 30 วัน** ตาม [DECISIONS](DECISIONS.md) และ `FORECAST_RULE` ค่า 50/90 ในโจทย์เดิมเป็นความผิดพลาด ไม่เปลี่ยน `MODEL_VERSION` |
| C2 | ขอบเขต Recommendation | Recommendation Engine คงขอบเขตเดิม (Behavior + Forecast + Goals ไม่รวม Anomaly และ Budget) ส่วนการจัดลำดับ 4 ชั้นย้ายไปเป็นชั้นแยกชื่อ **Alert Layer** (ข้อ 5) |

เรื่องที่เดิมยังไม่มีนิยาม **[ยืนยัน]**:
- **Runway → งบคงเหลือ:** ไม่ใช้ "เงินคงเหลือในบัญชี" เพราะแอปไม่รู้ยอดบัญชีจริง ให้ใช้ "งบคงเหลือ" ซึ่งระบบรู้แน่นอน (ข้อ 3.1) การคำนวณจากยอดบัญชีจริงที่ผู้ใช้กรอกเองเป็น future work
- **ชั้น 1 ทำงานเฉพาะเมื่อเหลือ ≤ 7 วันถึงวันเงินเข้า:** ช่วงนั้นอยู่ใน horizon ของพยากรณ์พอดี จึงไม่ต้องยืดพยากรณ์
- **คนที่เงินเข้าไม่แน่นอน:** fallback เป็นเดือนปฏิทิน ห้ามเดารอบจากรายรับล่าสุด (ข้อจำกัดที่รู้อยู่แล้ว ดูข้อ 3.0)

### C3-ทางเลือก (ตัดสินแล้ว: ก)

| ทาง | ทำอะไร | ข้อดี / ข้อเสีย |
|---|---|---|
| ก **[ยืนยัน]** | คงพฤติกรรมเดิม: Holt ใช้รายจ่ายทั้งหมด | ไม่เปลี่ยน `MODEL_VERSION` และ backtest เดิมใช้อ้างอิงได้ ผลรวมดีกว่า แต่ยอดกระโดดครั้งเดียวดึงพยากรณ์ขึ้น |
| ข | ตัดตาม flag อัตโนมัติ | ผล backtest แย่ลงโดยรวม และพังเมื่อพฤติกรรมเปลี่ยนจริง ไม่แนะนำ |
| ค | ตัดเฉพาะรายการที่ผู้ใช้ตัดสินแล้วว่า occasional / problem | ไม่ตัดตามการเดาของระบบ แต่ต้องมี backtest ใหม่ที่จำลองการตัดสินของผู้ใช้ และ `MODEL_VERSION` เปลี่ยน |

### ทิศทางใหม่หลัง backtest ข้อมูลจริง (31 ต.ค. 2026) — **[ทิศทาง ยังไม่ใช่การตัดสินใจ ยังไม่ implement]**

- **ต้นเหตุที่ Holt พุ่ง:** ระบบตรวจสอบรายการ (Anomaly) กับพยากรณ์นับรายการต่างกัน
  - Anomaly: รายการครั้งคราวถูกแยกเก็บ ไม่เข้า baseline หลัก ถ้าเกิดซ้ำด้วยแพทเทิร์นคล้ายเดิมหลายครั้ง ค่อยเข้า baseline ของรายการเกิดซ้ำ
  - พยากรณ์ (C3 = ก): นับรายจ่ายทุกรายการ รายการก้อนใหญ่ครั้งเดียวจึงถูก Holt อ่านเป็นแนวโน้ม (หลักฐาน: [FORECAST_REAL_DATA_BACKTEST](FORECAST_REAL_DATA_BACKTEST.md))
- **ทิศทาง:** ให้พยากรณ์ใช้กฎเดียวกับระบบตรวจสอบ คือทาง ค ตัดเฉพาะรายการที่**ผู้ใช้ยืนยันแล้ว**ว่าเป็นครั้งคราว ไม่ตัดตามที่ระบบ flag ทั้งแอปจะใช้นิยามเดียวว่ารายการไหนนับและไม่นับ
- **สถานะ:** C3 ใน [DECISIONS](DECISIONS.md) ยังล็อกไว้เป็น ก และยังไม่ได้แก้ การเปลี่ยนเป็น ค ต้องมีการยืนยันแยก หลังได้ผลเปรียบเทียบโมเดลตามแผนที่ประกาศล่วงหน้า และหลังตอบคำถามที่ยังเปิดอยู่สองข้อ คือ (ก) ระหว่างที่รายการถูก flag แต่ผู้ใช้ยังไม่ตรวจ พยากรณ์ควรทำอย่างไร และ (ข) รายการเกิดซ้ำรอบยาวควรเข้าพยากรณ์หรือไม่

## 1. สิ่งที่มีอยู่แล้ว **[ปัจจุบัน]**

- **`Profile`** (หนึ่งแถวต่อผู้ใช้ เขียนทับ): `income Decimal?`, `paydayDay Int?` (1–31 ถ้าเดือนสั้นกว่าใช้วันสุดท้ายของเดือน), `primaryGoalId`, `goal String?` (ความตั้งใจ ค่าจาก `FINANCIAL_INTENTIONS`)
- **`Budget`**: งบรวมรายเดือนปฏิทินต่อผู้ใช้ และ **`CategoryBudget`**: งบรายหมวด
- **`Goal`**: `targetAmount`, `targetDate`, `plannedMonthlyAmount` ยอดออมคิดจาก ledger (`GoalLedgerEntry`) ที่จัดสรรจาก**รายรับ** ไม่ได้มาจากรายจ่าย
- **`TransactionType`** มีแค่ `income` / `expense` ไม่มีประเภทโอนเข้าบัญชีออม
- **Forecast**: Theta (θ=2) ยอดรวมรายวัน, horizon 7, gate 30/30, `parameters` = `{ alpha, seasonalMode }` (เปลี่ยนจาก Holt 3 พ.ย. 2026 ดู [DECISIONS](DECISIONS.md); ข้อ C3 และ 4.2 ด้านล่างตัดสินตอนใช้ Holt และยังใช้กับ Theta)
- **`budgetComparison`** (backend เท่านั้น ถอดจากหน้า Forecast 4 พ.ย. 2026 ตามคำสั่งผู้ใช้ `forecastGoalSignal` ยังใช้): `referenceAllowance = max(งบคงเหลือ, 0) × k ÷ วันที่เหลือ` โดย `k = min(7, วันที่เหลือในรอบ)`
- **`calculateSavingsPlan`**: ตรวจ (รายได้ − งบ) เทียบยอดออมที่ต้องใช้ต่อเดือน แล้วเสนอ "ลดงบ" หรือ "เพิ่มรายได้"
- **Anomaly**: `AnomalyEvaluation.outcome = "flagged"` คือระบบตีว่าผิดปกติ ส่วน `AnomalyDecision.action` คือผู้ใช้ตัดสินแล้ว ค่าใน `ANOMALY_RULE` ล็อกแล้ว **[ยืนยัน]**

## 2. ส่วนที่ 1 — Financial Profile schema (เสนอ ยังไม่สร้าง)

แนวทาง: เพิ่มตาราง version แบบ append-only และคง `Profile` ไว้ ไม่ลบคอลัมน์เดิมในรอบนี้

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;  -- ใช้กับ exclusion constraint ด้านล่าง (D-16)

CREATE TYPE "PaydayMode" AS ENUM ('MONTHLY','SEMI_MONTHLY','IRREGULAR');

-- ชนิด text ตรงกับ User.id และ Goal.id จริง ลองรันกับฐานทดสอบ 3 พ.ย. 2026: uuid สร้าง FK ไม่ได้ แต่ text ผ่านครบ
CREATE TABLE "FinancialProfileVersion" (
  "id"              text PRIMARY KEY,
  "userId"          text NOT NULL REFERENCES "User"("id") ON DELETE RESTRICT,
  "effectiveFrom"   date NOT NULL,                 -- วันแรกที่ใช้ค่าชุดนี้ (เวลาไทย)
  "effectiveTo"     date,                          -- ไม่รวมวันนี้; NULL = ยังใช้อยู่
  "monthlyIncome"   numeric(12,2) CHECK ("monthlyIncome" >= 0),
  "primaryGoalId"   text,                          -- ยอดเป้าและกำหนดเวลาอ่านจาก Goal (C6)
  "intention"       text,                          -- ค่าเดิมจาก FINANCIAL_INTENTIONS ตรวจใน service layer (C4)
  "intentionNote"   varchar(500),
  "paydayMode"      "PaydayMode",
  "createdAt"       timestamptz(3) NOT NULL DEFAULT now(),
  FOREIGN KEY ("userId","primaryGoalId") REFERENCES "Goal"("userId","id") ON DELETE RESTRICT,
  CHECK ("effectiveTo" IS NULL OR "effectiveTo" > "effectiveFrom"),
  EXCLUDE USING gist ("userId" WITH =, daterange("effectiveFrom","effectiveTo",'[)') WITH &&)
);
CREATE UNIQUE INDEX ON "FinancialProfileVersion"("userId") WHERE "effectiveTo" IS NULL;

-- MONTHLY = 1 แถว, SEMI_MONTHLY = 2 แถว, IRREGULAR = 0 แถว (ใช้เดือนปฏิทิน)
CREATE TABLE "PaydayRule" (
  "versionId"  text NOT NULL REFERENCES "FinancialProfileVersion"("id") ON DELETE RESTRICT,
  "dayOfMonth" smallint NOT NULL CHECK ("dayOfMonth" BETWEEN 1 AND 31),
  PRIMARY KEY ("versionId","dayOfMonth")
);
```

ตาราง `PaydayExpected` ของร่างแรกถูกตัดออก เพราะ IRREGULAR ใช้เดือนปฏิทินแทน **[ยืนยัน]** และ enum ความตั้งใจใหม่ก็ถูกตัดออกตาม C4

กติกาการเขียน **[ยืนยัน]**:
- ห้าม UPDATE ค่าการเงินของแถวเดิม การแก้โปรไฟล์ทำใน transaction เดียว คือปิดแถวปัจจุบัน (`effectiveTo = X`) แล้ว INSERT แถวใหม่ (`effectiveFrom = X`) โดย X คือวันที่แก้ตาม D-1
- ยกเว้นแก้ซ้ำในวันเดียวกัน: แก้แถวของวันนั้นทับ ไม่สร้างแถวใหม่ D-1 ยังเป็นจริง และไม่ชน `effectiveTo > effectiveFrom` **[ยืนยัน 3 พ.ย. 2026]**
- การวิเคราะห์วันที่ d ใช้แถวที่ `effectiveFrom ≤ d < coalesce(effectiveTo, ∞)`
- จำนวนแถว `PaydayRule` ต้องตรงกับ `paydayMode` (ตรวจใน service layer)
- Migration: สร้างแถวแรกจาก `Profile` เดิม `effectiveFrom` ตาม D-2 แปลง `paydayDay` เดิมเป็น `MONTHLY` + 1 แถว และคัด `goal` ไปเป็น `intention` ตรง ๆ

## 3. ส่วนที่ 2 — Tier 0 metrics

### 3.0 ฟังก์ชันรอบกลาง (C5)

**เฟส 1 — ทำแล้ว 30 ต.ค. 2026 [ปัจจุบัน]:** [cycle.ts](../backend/src/lib/cycle.ts) เป็นที่เดียวที่ตัดสินว่า "รอบ" คืออะไร ตอนนี้คืนค่าเป็นเดือนปฏิทิน พฤติกรรมเหมือนเดิมทุกจุด

- API: `getCurrentCycle(date)`, `cycleByPeriod(year, month)`, `cycleByKey("YYYY-MM")`, `previousCycle(c)`, `cycleBounds(c)`, `getBudgetTimeline(year, month, today)`
- จุดที่เปลี่ยนให้เรียกผ่านฟังก์ชันนี้:

  - แจ้งเตือนงบ: `currentBudgetPeriod`, `transactionPeriod`, `checkBudgetMonth` (ใช้ที่ Settings ด้วย)
  - Forecast: `budgetComparison` และการดึงงบใน `forecastInput`
- ตรวจแล้วว่าผลเหมือนเดิม: [cycle.test.ts](../backend/tests/cycle.test.ts) เทียบกับโค้ดเก่าที่คัดลอกมาทั้งชุด ทุกวันตั้งแต่ 2023-12 ถึง 2029-01 รวมถึง timeline ของเดือนที่ผ่านมา เดือนปัจจุบัน และเดือนอนาคต ผ่านครบ และ pure tests ที่เกี่ยวข้อง (forecast, goals, budget notifications, dashboard) 54 tests ผ่านทั้งหมด ไม่ได้รัน database/browser tests

### 3.1 นิยามรอบ (เฟส 2)

ให้ `P₀ ≤ วันนี้ < P₁` เป็นวันเงินเข้าสองครั้งติดกัน (เวลาไทย, เดือนที่ไม่มีวันนั้นใช้วันสุดท้ายของเดือน ตาม `paydayDate`) ในเฟส 1 คือวันแรกของเดือนนี้และวันแรกของเดือนถัดไป

- `cycleDays = P₁ − P₀` (วัน)
- `elapsed = วันนี้ − P₀ + 1` (วัน, รวมวันนี้)
- `daysLeft = P₁ − วันนี้` (วัน, รวมวันนี้)
- `spent = Σ รายจ่ายใน [P₀, วันนี้]` (บาท)
- `cycleBudget` (บาท/รอบ) = งบต่อเดือนจาก `Budget` (D-15) รอบนี้เป็นเดือนปฏิทิน จึงเท่างบเดือนพอดี สัดส่วนรอบ D-4 ใช้เมื่อมีเฟส 2

### 3.2 งบคงเหลือรายวัน (แทน runway) **[ยืนยันแนวทาง]**

`budgetLeft = max(cycleBudget − spent, 0)` (บาท) · `perDay = budgetLeft ÷ daysLeft` (บาท/วัน)
ข้อความ: "งบเหลือ 800 ใช้ได้วันละ 160" `perDay` ปัดลงเป็นบาทเต็มเท่านั้น ห้ามปัดขึ้นเพราะจะเกินเพดาน และไม่ใช้กฎปัดของ D-8 เพราะค่านี้มาจากงบ ไม่ใช่พยากรณ์ ต่ำกว่า 1 บาทไม่แสดงตัวเลข ใช้งบเหลือแทน หน้า Forecast ใช้กฎเดียวกัน ถ้าใช้เกินงบแล้ว แสดงยอดที่เกินแทน ห้ามแสดง "ใช้ได้วันละ 0"

### 3.3 Budget pace

`expectedSpent = cycleBudget × elapsed ÷ cycleDays` (บาท) · `paceGap = spent − expectedSpent` (บาท; บวก = ใช้เร็วกว่าแผน)

### 3.4 Goal feasibility (ใช้ `calculateGoal` เดิมคำนวณ `required`)

`required = (targetAmount − saved) ÷ monthsLeft` (บาท/เดือน) · `available = monthlyIncome − งบต่อเดือน` (บาท/เดือน) งบมาจากแหล่งเดียวตาม D-15
ถ้า `required > available` ให้ `shortfall = required − available` แล้วเสนอ:
- ลดงบ: `งบต่อเดือน − shortfall` (แสดงเฉพาะถ้า ≥ 0)
- ยืดเวลา: `ceil((targetAmount − saved) ÷ available)` เดือน (แสดงเฉพาะถ้า `available > 0`)
- ลดยอดเป้า: `saved + available × monthsLeft` (แสดงเฉพาะถ้า `available > 0`)
- ยืดเวลาและลดยอดเป้าแสดงเฉพาะเมื่อมีเป้าเดียว เพราะหลายเป้าใช้เงินเหลือก้อนเดียวกัน ถ้าหลายเป้าต้องบอกเหตุผลที่ไม่มีสองตัวเลือกนี้ **[ยืนยัน 3 พ.ย. 2026]**
- เพิ่มรายได้ (มีอยู่เดิม): D-17

**4.1 หน้าต่าง 7 วัน ตัดที่วันเงินเข้า**
`W = [วันนี้, วันนี้ + 6]` ถ้า `P₁ ∈ W` แบ่งเป็น `S₁ = [วันนี้, P₁ − 1]` และ `S₂ = [P₁, วันนี้ + 6]`
- `forecast(S)` = ผลรวมพยากรณ์รายวันในช่วง S (บาท)
- `allowance(S₁) = budgetLeft ÷ daysLeft × |S₁|` (สูตรเดิมของ `referenceAllowance` ที่ตอนนี้อ่านปลายรอบจาก `getCurrentCycle` แล้ว)
- `allowance(S₂) = nextCycleBudget ÷ nextCycleDays × |S₂|` ใช้งบของรอบใหม่
- `overshoot(S) = forecast(S) − allowance(S)` เทียบทีละช่วง ห้ามรวม 7 วันแล้วเทียบกับงบของรอบเก่า

**4.3 Fallback ก่อน Forecast Gate (30/30)**
`typicalDaily = มัธยฐานของยอดรวมรายวัน (เฉพาะวันที่มีรายการ) × (จำนวนวันที่มีรายการ ÷ จำนวนวันที่นับ)` (บาท/วัน) โดยนับตั้งแต่วันแรกที่มีรายการถึงเมื่อวาน ภายใน 30 วันล่าสุด และ `estimate(S) = typicalDaily × |S|` **[ยืนยัน D-9]**
เงื่อนไข: ย้อนดู 30 วัน บันทึกมาแล้วอย่างน้อย 7 วัน และมีรายการอย่างน้อย **3 วันที่ต่างกัน** ถ้าไม่ถึงให้แสดง "ข้อมูลยังไม่พอ" ใช้เลข 3 เพราะเป็นจำนวนน้อยที่สุดที่ค่าสุดโต่งค่าเดียวเป็นมัธยฐานไม่ได้ (ถ้า 1 วัน มัธยฐานคือค่านั้นเอง ถ้า 2 วัน มัธยฐานคือค่าเฉลี่ย) ไม่ใช่ค่าที่ตั้งเอง ไม่ต้องตัดรายการผิดปกติ (D-11)

ข้อจำกัดของ fallback (บันทึกตามจริง):
- **แยกไม่ได้ว่าไม่มีรายจ่ายจริง หรือผู้ใช้บันทึกไม่ครบ:** แอปเห็นแค่สิ่งที่ถูกบันทึก ถ้าบันทึกไม่ครบ ตัวคูณความถี่จะต่ำลง ค่าประมาณจึงต่ำไป ผลคือเตือนน้อยไป ไม่ใช่เตือนผิด
- **ยอดใหญ่ 2 วันจาก 3 วันยังลากค่าอยู่:** มัธยฐานกันได้เฉพาะเมื่อยอดใหญ่ไม่ถึงครึ่งของวันที่มีรายการ
- **ผู้ใช้ใหม่ที่บันทึกยังไม่ถึง 3 วันจะเห็น "ข้อมูลยังไม่พอ"** แต่ไม่ต้องบันทึกติดกัน (ต่างจากมัธยฐานแบบนับวันที่ไม่มีรายการเป็น 0 ซึ่งร่างก่อนหน้าเสนอไว้ แบบนั้นกระทบผู้ใช้ใหม่เกือบทุกคน)
- **ไม่เลือก trimmed mean:** ต้องตั้งสัดส่วนที่จะตัด ซึ่งเป็นตัวเลขที่ตั้งเองโดยไม่มีข้อมูลรองรับ
- **ไม่เลือกเพดานต่อรายการ:** ต้องตั้งเกณฑ์ว่าใหญ่แค่ไหน ซึ่งซ้ำกับงานของ Anomaly และขัดกับหลักแยก input ของ C3
ข้อความแยกจากโมเดลพยากรณ์ (Theta): "จากที่ใช้จริงปกติวันละประมาณ 300 บาท ถ้าใช้เท่านี้ต่อไปจะเกินงบที่ควรใช้"

## 5. ส่วนที่ 4 — Alert Layer (ไม่ใช่ Recommendation) **[ยืนยันการแยกชั้น]**

**Alert Layer คืออะไร:** ชั้นสรุปสถานะว่าตอนนี้มีเรื่องการเงินอะไรที่ควรรู้ เรียงตามความเร่งด่วน อ่าน Budget, Forecast, Goal และ Anomaly ได้ ไม่ได้สร้างคำแนะนำพฤติกรรม

**ต่างจาก Recommendation Engine ตรงไหน:**

| | Recommendation Engine | Alert Layer |
|---|---|---|
| ขอบเขตข้อมูล | Behavior + Forecast + Goals ตาม [DECISIONS](DECISIONS.md) ไม่แก้ | Budget pace, Forecast, Goal feasibility, Anomaly ที่ยังไม่ตัดสิน |
| คำถามที่ตอบ | "ควรปรับพฤติกรรมอะไร" | "ตอนนี้มีอะไรเร่งด่วน" |
| ผลลัพธ์ | คำแนะนำ | รายการสถานะเรียงลำดับ พร้อมสิ่งที่ทำต่อได้ |
| ความสัมพันธ์ | ไม่อ่านผลของ Alert Layer | ไม่สร้างหรือแก้คำแนะนำ |
