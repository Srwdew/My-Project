## ข้อกำหนดที่ยืนยันแล้ว

**เกณฑ์ปลดล็อกนับถึงเมื่อวาน (ยืนยัน 5 พ.ย. 2026):** Forecast และ Behavior ตั้งใจไม่นับวันนี้ เพราะวันที่ยังไม่จบจะทำให้พยากรณ์เพี้ยนและเทียบช่วงไม่เท่ากัน ส่วนแถบปลดล็อกและตัวเลข "ขาดอีก" แสดงรวมวันนี้เพื่อให้ผู้ใช้เห็นผลทันที (`progressWithToday`) ค่าที่แสดงนี้ไม่ได้ตัดสินการปลดล็อก ถ้าวันนี้ทำให้ตัวเลขครบแต่เกณฑ์จริงยังไม่ผ่าน แถบค้างที่ 99% หัวข้อเป็น "ครบแล้ว" (กรณีที่ห้า แยกจากช่วง 90–99%) และบอกว่า "ครบตามจำนวนแล้ว ระบบจะเริ่มวิเคราะห์เมื่อข้อมูลพร้อม" ไม่ระบุวัน เพราะช่วงของ Behavior เลื่อนทุกวัน รายการเก่าสุดอาจหลุดจนตัวเลขถอยและยังไม่ปลดล็อก แบนเนอร์และแถบต้องใช้ตัวเลขชุดเดียวกัน

**ประโยคที่พิจารณาแล้วไม่ใส่ (5 พ.ย. 2026):** "ถ้ารายการเก่าเกินช่วงที่นับ ตัวเลขอาจเปลี่ยน" ไม่ใส่เพราะการ์ดจะยาวขึ้น จะใส่เมื่อเจอผู้ใช้สับสนจริง

สำหรับ Behavior ผู้ใช้ยืนยันในงานก่อนหน้าของบทสนทนานี้:

|---|---|

| ทั่วไป | 5 วันที่แตกต่างกันภายใน30วัน |
| รายสัปดาห์ | 4 ครั้งภายใน28วัน ห่างกัน 7±1 วัน (ยืนยัน 24 ต.ค. 2026) |
| รายเดือน | 3 ครั้งภายใน90วัน แต่ละครั้งห่างจากวันครบรอบไม่เกิน ±3 วัน; วันครบรอบ = วันเดียวกับครั้งแรก (ปรับเป็นสิ้นเดือนถ้าเดือนสั้นกว่า) หรือสิ้นเดือนถ้าครั้งแรกเป็นสิ้นเดือน (ยืนยัน 24 ต.ค. 2026) |

| ขั้นต่ำของยอดเพิ่ม | ข้อค้นพบรายหมวดต้องเพิ่ม >=5% ของช่วงก่อน **และ** >=100 บาท ทั้งสองเงื่อนไข; ต่ำกว่านั้นเป็นข้อเท็จจริงเท่านั้น (ยืนยัน 24 ต.ค. 2026) |

| ข้อความ | แยกข้อมูลไม่พอกับตรวจแล้วไม่พบ คงเหตุผลระดับหมวด; ไม่อ้างนัยสำคัญ/สาเหตุจากยอดเพิ่มเล็กน้อย; ยอดลดเป็นข้อเท็จจริง |
| การแยกโมดูล | ไม่ใช้ Anomaly recurrence thresholds ทับ Behavior และไม่เปิด collection/automatic matching |

ค่าด้านบนลงโค้ดเป็น `behavior-v3` ใน [behaviorRules.ts](../backend/src/lib/behaviorRules.ts) (`amountTolerance`, `weeklyDateTolerance`, `monthlyDateTolerance`, `minimumIncreaseShare`, `minimumIncreaseAmount`, `dominantShare`) ค่า 10% เป็นค่าของ Behavior เอง ไม่ได้นำ helper 15% ของ Anomaly มาใช้

ข้อกำหนดอื่นที่ผู้ใช้ยืนยัน 24 ต.ค. 2026:
- แผนงานหลักใช้ 8 ขั้นแทนแผน 11 ข้อเดิม: Database Schema → Authentication & Financial Profile → Transaction Core (Manual Entry) → OCR Upload Flow → Data Readiness Check → Core Financial Metrics → Analytics Pipeline → Recommendation Engine & Dashboard
- ตัวเลข Anomaly ใน `ANOMALY_RULE` ([anomalyRules.ts](../backend/src/lib/anomalyRules.ts)) และค่าผ่อนผัน `CADENCES` ([anomalyPatternPolicy.ts](../backend/src/lib/anomalyPatternPolicy.ts)) ล็อกตามค่าปัจจุบัน และใช้แทนกฎเดิม
- Recommendation Engine ครอบคลุม Behavior, Forecast และ Goals (ไม่รวม Anomaly และ Budget); รายละเอียดกฎคำแนะนำยังไม่ได้กำหนด

นิยาม evidence containment เป็นวิธี implementation ที่ได้ทำและทดสอบแล้วในงานก่อนหน้า ไม่ใช่ค่าความคลาดเคลื่อนที่ผู้ใช้กำหนดใหม่ ตั้งแต่ `behavior-v3` เทียบ containment ด้วย transaction id ของหลักฐาน แทนการเทียบยอดตรงกัน ดู [เอกสาร Behavior](../BEHAVIOR_IMPLEMENTATION.md) สำหรับรายละเอียด counts/วัน/earliest witness และข้อจำกัดการไม่แจกแจงทุก episode

ข้อกำหนดการทำงานใน repository จากผู้ใช้: รักษา local changes; ไม่แตะฐานหลักในการทดสอบที่กำหนดให้ใช้ฐานแยก; ไม่ reset ฐานโดยไม่ได้รับอนุญาต; งานเอกสารรอบนี้ห้ามแก้ source/schema/migration และ commit/push

### Financial Profile, Tier 0 และ Alert Layer (ยืนยัน 30 ต.ค. 2026)

รายละเอียดสูตรและ DDL อยู่ใน [FINANCIAL_PROFILE_DESIGN](FINANCIAL_PROFILE_DESIGN.md) ส่วนนี้บันทึกเฉพาะสิ่งที่ผู้ใช้ยืนยัน ยังไม่ได้ implement นอกจาก C5 ที่ระบุไว้

- หลักทั่วไป: ถ้าโจทย์ขัดกับเอกสารโปรเจกต์ ให้ยึดเอกสารโปรเจกต์แล้วแจ้งผู้ใช้
- C1: Forecast Gate คงที่ 30 รายจ่าย / 30 วัน ตาม `FORECAST_RULE` (ค่า 50/90 ในโจทย์เป็นความผิดพลาด)
- แผนงาน (3 พ.ย. 2026): งานบังคับคือ Tier 0, Alert Layer, การ์ด Alert และ fallback D-9 ตาราง version เป็นตัวเลือก ตัดสินหลังการ์ด Alert เสร็จ ถ้าเกิน 10 วันให้ตัด **ตัดเฟส 2 และเงินเข้าสองงวดออกจากแผน** ดูข้อจำกัดในข้อ 5 ของ design
- Tier 0 (ยืนยัน 3 พ.ย. 2026): **วงเงินต่อวันทุกที่ใช้กฎเดียวกัน** ทั้ง `perDay` และแถววงเงินต่อวันของหน้า Forecast ปัดลงเป็นบาทเต็ม เพราะมาจากงบและการปัดขึ้นจะเกินเพดาน ไม่ใช้ D-8 ต่ำกว่า 1 บาทไม่แสดงตัวเลข ใช้ `budgetLeft` บอกยอดเหลือแทน เพราะ "วันละ 0" ผิดความจริงเมื่อยังเหลือเงิน
  - ยืดเวลาและลดยอดเป้าแสดงเฉพาะเมื่อมีเป้าเดียว เป้าหลายตัวใช้เงินเหลือก้อนเดียวกัน ถ้าคิดแยกจะนับซ้ำ แต่ละเป้าจะดูไปรอดทั้งที่รวมกันไม่รอด กรณีหลายเป้าแสดงลดงบกับเพิ่มรายได้ และต้องบอกเหตุผลว่าทำไมไม่มีสองตัวเลือกนั้น (`goalOptionsUnavailable`)
  - ต่างจากข้อ 3.4: เอกสารกำหนด `available > 0` เฉพาะยืดเวลา แต่โค้ดไม่คืนลดยอดเป้าด้วยเมื่อเงินเหลือไม่เป็นบวก เพราะยอดเป้าใหม่จะต่ำกว่าเงินที่ออมแล้ว ซึ่งไม่มีความหมาย
- กราฟพยากรณ์ (ยืนยัน 4 พ.ย. 2026): ใช้ theta-split เฉพาะการแสดงกราฟ (`summary.chartDaily`) ตรรกะอ่าน `daily` เดิม ไม่เปลี่ยน `MODEL_VERSION` weekday-mean เป็นงานต่อยอด ดู FORECAST_REAL_DATA_BACKTEST 5.6
- หมวดที่ลดได้ (4 พ.ย. 2026): ก่อนหน้านี้ไม่มีหน้าจอหรือ API ให้ผู้ใช้เลือก R1, R7, R9 จึงไม่เคยทำงานกับผู้ใช้จริง เพิ่ม `/category-flags` และส่วนเลือกในหน้า Settings แล้ว กล่องเชิญมีลิงก์ไปที่นั่น
- ตำแหน่งแสดงผล (คำสั่งผู้ใช้ 4 พ.ย. 2026): การ์ด Alert ไปอยู่ในกระดิ่ง (ชนิด `alert_layer`, key ต่อรอบ ตัวเลขคงตามตอนที่แจ้งครั้งแรก) คำแนะนำออกจาก Overview: R3/R4/R5/R9 ที่ Behavior, R1/R2 ที่ Forecast, R6/R7/R8 ที่ Goals เพดาน 3 ข้อต่อหน้า เอนจินยังจัดลำดับและกันซ้ำรวมทุกกฎ R1 จึงยังตัด R5 แม้อยู่คนละหน้า ไม่ต้องเปลี่ยนตรรกะ
- Alert Layer (ยืนยัน 3 พ.ย. 2026):
  - **ป้าย Goals กับชั้น 3 ขัดกันได้โดยตั้งใจ** ชั้น 3 ถามว่าแผนเป็นไปได้ไหม (รายได้ในโปรไฟล์ − งบ, D-13) ป้าย Goals ถามว่าที่ผ่านมาทำได้จริงไหม (เงินสุทธิจริงเดือนก่อน) ทุกข้อความต้องบอกฐานของตัวเอง ห้ามซ่อนป้ายและห้ามเปลี่ยน D-13 ตัวอย่าง ต้องออม 8,000/เดือนทั้งสองกรณี ก: รายได้ 30,000 งบ 20,000 เดือนก่อนรับ 25,000 จ่าย 24,000 ชั้น 3 เงียบ แต่ป้ายขึ้น ข: รายได้ 30,000 งบ 29,000 เดือนก่อนรับ 40,000 จ่าย 15,000 ชั้น 3 ขึ้น แต่ป้ายเงียบ
  - **R1 กับชั้น 2 ขึ้นพร้อมกันได้โดยตั้งใจ** R1 ถามจากเงินที่มีจริง ชั้น 2 ถามจากงบที่ตั้งไว้ ไม่ให้ frontend ซ่อนใบใด เพราะจะย้ายการตัดสินไปชั้นที่ไม่ควรมี ใช้หัวข้อสองส่วนต่างกันชัดเจนแทน
  - ตีความเพิ่มจากเอกสาร: `forecast(S)` ที่รวมวันนี้นับเฉพาะส่วนที่วันนี้อาจเพิ่ม (พยากรณ์วันนี้ − ยอดที่บันทึกแล้ว ไม่ต่ำกว่า 0) เพราะ `budgetLeft` หักยอดวันนี้แล้ว และให้ตรงกับ `budgetComparison`
  - ตรวจจากภาพจริงแล้ว (4 พ.ย. 2026): ผู้ใช้ยืนยันว่า R1 กับชั้น 2 ขึ้นพร้อมกันไม่สับสน

  - ถ้อยคำตามความตั้งใจ (ข้อ 5 ของ design) **เลื่อน ไม่ใช่ตัด** ทำหลังการ์ดใช้งานได้ เพราะไม่กระทบตรรกะหรือลำดับ
